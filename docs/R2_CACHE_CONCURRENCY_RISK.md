# R2 缓存后台读取并发风险与验收要求

## 当前结论

核验时间：2026-10-23 04:08 UTC。核验主线：`fb3297d5052c47d325230c270bd9c6fa730135dd`（[PR #22 合并提交](https://github.com/ForceMind/ZapIME/commit/fb3297d5052c47d325230c270bd9c6fa730135dd)）。

**状态：源码风险尚未修复，建议部署前完成修复与专项验收。** 本文仅记录问题与验收要求，不修改服务实现，不表示已完成修复。

[PR #22 的 P1 评审](https://github.com/ForceMind/ZapIME/pull/22#discussion_r4355312082)指出，已取消请求遗留的缓存回源没有独立并发上限。核验时该线程仍未解决，主线仍保留对应实现。P1 是该评审给出的优先级，不是线上事故等级。

这是静态源码与评审发现。没有证据表明用户服务器已部署该版本、遭受利用或产生额外费用；也没有在真实 R2、生产服务器或用户设备上执行复现。PR #22 记载的 PostgreSQL/S3 兼容服务验收不能作为真实 Cloudflare 部署证据。

## 触发条件与执行路径

风险针对启用了在线对象缓存的 S3/R2 读取路径，需同时具备：

1. 请求通过账号与设备鉴权，数据库中存在该账号可访问的对象引用。
2. 目标对象缓存未命中，后端读取已经开始。
3. 调用方在后端读取完成前取消或断开请求。
4. 后续请求命中不同的未缓存对象，且先前后台读取仍在执行。

[缓存 Get](https://github.com/ForceMind/ZapIME/blob/fb3297d5052c47d325230c270bd9c6fa730135dd/services/sync/internal/syncapi/object_cache.go#L100-L139)通过 `singleflight.DoChan` 合并同键读取，再用 `context.WithoutCancel(ctx)` 脱离调用方取消，为共享 fetch 单独设置 5 秒期限。调用方的 `ctx.Done()` 就绪后，`Get` 可以先返回，后台读取则继续。

[HTTP handler](https://github.com/ForceMind/ZapIME/blob/fb3297d5052c47d325230c270bd9c6fa730135dd/services/sync/internal/syncapi/http.go#L67-L77)的槽位在返回时释放；因此新请求可进入，而之前启动的不同 key 的后台 fills 尚未结束。实际累计量受请求到达速度、后端延迟、可访问对象数量、机器资源等影响，但源码没有给这些遗留 fills 设置固定的进程级并发上限。这里的“无界”指缺少该硬上限，不表示单次读取永久运行或实测能够达到无限数量。

## 影响与现有限制为何不足

可能增加后台 goroutine、连接、内存占用及 R2 读取操作数，影响服务可用性；超出适用免费额度时可能增加费用。本文不估算实际费用，也不声称存在数据泄露或鉴权绕过。

- **HTTP 的 32 个槽位**限制正在执行的 handler，不覆盖 handler 返回后仍存活的 fetch。见 [API 构造](https://github.com/ForceMind/ZapIME/blob/fb3297d5052c47d325230c270bd9c6fa730135dd/services/sync/internal/syncapi/http.go#L15-L20)与上述释放逻辑。
- **每次 Pull 的 8 个工作者**是单次调用内的限制。[decodeChanges](https://github.com/ForceMind/ZapIME/blob/fb3297d5052c47d325230c270bd9c6fa730135dd/services/sync/internal/syncapi/objects.go#L246-L295)中的工作者可在缓存 Get 因取消返回后退出，不能继续代表后台 fill 持有全局容量。
- **singleflight**只合并相同 key。不同账号或不同对象 key 不共享一次读取；它不是跨 key 的容量限制。
- **5 秒 fetch 期限与 4 秒 HTTP client timeout**限制生命周期，不限制这段时间内新建的任务数。后端仍须遵守 context 取消；不能把超时当作任意后端实现的强制终止保证。
- **MaxIdleConnsPerHost = 8**仅限制空闲连接保留数量，不是活动连接数上限。[S3 transport 配置](https://github.com/ForceMind/ZapIME/blob/fb3297d5052c47d325230c270bd9c6fa730135dd/services/sync/internal/syncapi/objects.go#L67-L74)没有设置独立 fill semaphore。
- **16 MiB LRU 预算**约束已缓存条目，不覆盖所有在途读取、等待者与 goroutine。
- **账号事务锁与存储配额**仍有其授权、一致性和容量作用，但后台 fill 脱离请求后，这些机制不能替代其生命周期内的并发上限。

正常的同键共享读取仍有价值。修复不能通过让首个调用方断开就取消其他仍在等待的设备来破坏此语义。

## 建议修复契约

以下是待实现、待评审的建议，不是已接受的实现或已完成能力。

1. 为在线缓存 fills 设置覆盖所有 key、账号和请求的**进程级有界执行容量**，并明确容量值及多进程部署时的总量。容量应从后台工作准入起持有到后端真正返回，在成功、失败和超时等路径都释放；不能随单个 handler 返回提前释放。
2. 同时约束等待准入的任务与 goroutine。仅在每个新建 goroutine 内等待 semaphore，仍可能形成无界等待队列。采用有界队列、可取消等待或明确拒绝策略，定义过载错误及调用方退避，不把过载伪装成成功空页。
3. 明确共享取消语义：单个等待者取消只移除该等待者；仍有等待者时保留共享读取。没有等待者时，可选择取消后端，或允许在上述容量与期限内完成预热。若取消后端，容量仍应等实际工作退出再释放。
4. 覆盖最后一个等待者离开、新等待者加入、完成与取消同时发生等竞态。保留同键合并、独立返回副本、错误不缓存、SHA 校验、先鉴权后缓存及实际持久写确认。
5. 评估进程级限制之外的按账号公平性、入口速率限制和操作数监控。它们用于纵深防护；单一进程并发上限并不等于所有副本的总量上限或账单硬停。

## 确定性回归验收

**本节是未来修复的验收计划，本文没有新增或运行这些测试。** 仅使用合成对象和可控内存后端，不连接真实 R2，不做生产压测或攻击测试。

- 后端提供开始通知、显式释放屏障、context 取消观察、当前活动数与峰值计数。测试使用小容量，例如 2，有限数量的不同 key；用同步屏障控制时序，避免依赖任意 sleep。测试整体必须有截止期限与清理逻辑。
- 先确认后台读取已经开始，再取消各自调用方。保持后端未返回，提交额外不同 key 的请求，断言所有活动 fills 的峰值始终不超过配置容量；同时断言等待队列/准入任务的数量或拒绝行为满足设计上界。只检查最终请求数不足以证明并发受限。
- 释放一个后端读取后，只允许相应容量的新工作进入。成功、后端错误、期限到达和取消均不泄漏容量，后续正常请求可以恢复；清理后所有测试自建任务退出。
- 同 key 两个等待者中取消一个，另一个仍可取得正确结果，后端读取次数为一次。所有等待者取消时，严格验证所选择的“取消后端”或“有界完成预热”契约，以及新等待者加入的竞态。
- 覆盖缓存命中、过期、损坏、失败重试、跨账号隔离及撤销；确认新限流不会使失败页被当成空页推进 cursor。
- 在隔离测试环境增加 HTTP 取消到缓存后端的集成回归，验证 handler 槽位已释放时，遗留 fills 仍受独立容量限制。需要数据库时使用专用合成 PostgreSQL 夹具，按仓库规范清理自己创建的引用，不访问真实对象桶。
- 在修复的准确提交上运行对应 Go race 测试、重复专项回归和相关服务门禁，保存命令、提交 SHA、结果与未执行项。测试必须能在原问题版本上暴露缺少容量边界，而非只在修复版本上通过。

## 现有验证的边界与关闭标准

[已有取消与 32 读者测试](https://github.com/ForceMind/ZapIME/blob/fb3297d5052c47d325230c270bd9c6fa730135dd/services/sync/internal/syncapi/object_cache_test.go#L120-L155)验证同一 key 的共享读取，不覆盖不同 key 反复取消后的全局容量。PR #22 的 [服务 CI 39885955906](https://github.com/ForceMind/ZapIME/actions/runs/39885955906)通过，不能证明未包含的场景安全，也不能作为本问题已修复的证据。CI 绿色与评审线程解决状态都不能替代修复代码和对应回归证据。

关闭此风险需补充：

- 修复 PR、准确提交 SHA 与实现的容量/排队/取消契约；
- 上述不同 key 取消回归及同键共享语义的实际通过证据；
- 相关既有门禁结果与仍未覆盖的部署条件；
- 在重新核验后更新本文状态，并在原评审线程说明处理依据。

即使修复通过，真实 Cloudflare、生产部署、多实例总量、运维限流和费用监控仍须分别验证，不能自动标为完成。相关背景见 [同步用量](SYNC_EFFICIENCY.md)、[服务部署](SERVER_DEPLOY.md)与 [技术决策](DECISIONS.md)。
