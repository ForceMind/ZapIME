# A3 · Android 登录与自动加密同步实施计划

2026-11-24。用户已确认[三屏视觉及交互](design/ANDROID_ACCOUNT_SYNC.md)与四步实施方案。当前在 A3.1，主机 OIDC 验证通过，Android 回跳和 Go 设备授权分别验收。

## 起点与首个成果

现有 Android 已有手动设备连接、密钥准备、恢复文件及显式逐轮同步。Go 服务使用管理员分配的设备凭据。A2 [草稿 PR #125](https://github.com/ForceMind/ZapIME/pull/125) 的 `8644f98` 已通过真实 Go、PostgreSQL、HTTPS 和双 SQLite 验收，当前仍开放且未合入 `main@4dd72a4`。它验证了共享 Rust 终止页、首次发布和回执边界。Android 当前 JNI 提供 `applySyncPage`、`stageSyncUpload`、`ackSyncUpload`，尚需接入首次发布的终止证明和自动授权。[手动同步契约](ANDROID_MANUAL_SYNC.md) · [A2 运行](https://github.com/ForceMind/ZapIME/actions/runs/45395869314)

**首个可见成果。** API28 上完成真实账号登录并返回主 App，看到已核实的账号、服务器与设备授权。选择「仅登录」时，个人资料上传数为零。

**首个可操作成果。** 在隔离的真实登录服务与同步服务器中，A 在主 App 点一次「登录并开启同步」，一条由 A 端本机创建的合成快捷短语走日常队列并自动加密上传，A 显示该版本的服务器回执。已获同一账号授权且已恢复同一把密钥的 B 端在前台自动拉取并解密。若 B 是同模拟器的一份独立资料库，结果记为双资料库，物理双设备另记证据。来源可验证且无原待发操作的旧资料单独验收。

## Sol 执行顺序

| 步骤 | 交付物 | 验收及停止条件 |
| --- | --- | --- |
| 1. 真实登录与设备授权 | 推荐由部署者配置 OIDC。Android 使用系统浏览器、Authorization Code 和 PKCE `S256`。Go 在验证面向同步登录端点的短时访问令牌后，将可信身份映射到已有账号。设备使用独立授权，沿用 `/v1/session` 核对。 | 先在隔离环境证明 API28 的真实回跳、登录凭证可验证及首次设备授权，再接入主 App。用户可完成真实登录并看到实际账号、服务器与设备状态。取消、错误签发者、受众、账号及设备重放均失败。登录流程零资料传输。 |
| 2. 密钥就绪与同步开关 | 复用现有 Android Keystore、恢复文件与本机绑定。保存本设备的同步同意和失效代次，接入「仅登录」、开启、关闭及缺密钥状态。 | 登录成功后能区分已关闭、待设备授权、待密钥和可同步。错误恢复码、换号、异根、撤销以及中途关闭均无法放行资料传输。重新打开时只恢复可验证的本机同意。 |
| 3. 打通一次真正的自动同步 | 先接现有正常待发队列，再接来源可验证且无原待发操作的存量发布。在 A2 安全基础上将 `SyncRound` 的有界拉取、冻结请求、ACK 与 Android 前台触发串起来。 | 日常同步跑通首个双端短语闭环。存量另用初始待发为零、预先可证来源的资料验收，验不到可信来源时记录该路径待解决。另测非终止页、来源未知的备份、重复触发、未授权与丢回执。 |
| 4. 补齐状态和回归 | 落实状态详情、断网恢复、关闭/退出/切换账号和冲突提示。保持当前输入路径与手动同步兼容。 | 核对真实 UI、Go/PostgreSQL/HTTPS、API28 正向与拒绝证据及 API35/36 适用回归各自的结果。发布范围内的任何未运行项保持明确。通过本阶段门禁后才进入 A4 试用。 |

### 1. 账号登录、设备授权分别验证

- 首版只接一个由部署者固定配置的 issuer、客户端和同步登录 API 受众，优先采用经验证的 Android App Link。回跳域名由能配置当前 Android 包名和签名关联的部署者掌控，可与同步服务域独立。先实测 API28/API36 系统浏览器回跳，并确认身份服务能签发同步登录端点可验证的 OAuth 访问令牌。OIDC 身份映射使用固定 issuer 与可信 subject，在配置阶段验证它在预期令牌中的稳定性。邮箱只用于显示。计划采用专用的 RFC 9068 访问令牌，服务校验类型、签名、issuer、audience、客户端、scope、有效期与用户授权上下文。Android 不用 ID token 作为同步登录 API 的权限凭据。[OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability) · [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252) · [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700) · [RFC 9068](https://www.rfc-editor.org/rfc/rfc9068.html#section-4)
- 回跳只接受已登记的精确地址和当前尚未消费的登录请求，校验 `state`、PKCE 和对应登录代次。回跳域的 `assetlinks.json` 与实际 Android 包名和签名匹配。需保留真实浏览器打开与返回主 App 的两段证据。[Android App Links](https://developer.android.com/training/app-links/configure-assetlinks)
- 首版账号和首个 owner 由管理员沿用现有 `provision` 建立，管理员预先将核实的 `(issuer, subject)` 显式绑定到已有 ZapIME `account UUID`。登录返回的主体或服务与用户看到的不同，展示实际目标并重新取得同意。尚未绑定的主体显示「此服务器账号尚未授权」。账号归属和角色由服务端授权决定。
- 新安装仅在已有 owner 明确批准后取得设备凭据。设备登记记录绑定登录主体、账号、发起设备的本机密钥证明和有效期，服务端原子消费一次，并只把凭据交给通过该证明的申请设备。管理员绑定、owner 批准和设备领用分别验收。已接入设备通过既有 `/v1/session` 检查身份、期限和撤销。登录顺序、凭据签发失败或响应丢失必须可恢复，不能重复生成活动设备、重新启用被撤销设备或静默替换现有凭据。根密钥和恢复码只在客户端处理。

### 2. 密钥、授权和取消边界

- 先验证账号和设备授权，再分支处理远端密钥：已登记账号恢复原材料并匹配公开描述符。无历史空账号复用现有 owner 逐次明确登记。异根、缺材料且远端不匹配、落在旧历史、现有 SQLite 绑定其他账号时暂停。相关密钥操作沿用专用同步 worker 和独立 Keystore 域。
- 同意只覆盖用户看见的服务器、账号、设备、资料范围与稳定密钥身份。等待恢复时可持久记录已登记的预期密钥，完成本机材料和库绑定验证后才可以传输。登录失败或取消、仅登录、换目标及换密钥均不能复用旧同意。开关授权不会随资料备份或密钥恢复文件转移。
- 关闭、退出或切换需先使当前代次失效并停止接纳新网络操作。队列任务、异步登录和恢复回调都重核当前代次。已送达的请求可能完成，保留原始冻结字节，后续在同一授权目标核实。持久授权与数据库检查要在会产生副作用的边界复核，进程内状态仅用于调度。

### 3. 首次对账与后续自动同步

- 实现前回读 A2 状态。用合入后的基线或经仓库审查的明确依赖纳入其验收，确认第 3 步的提交确实包含 A2 的范围与证据。第 1、2 步可用当前基线先完成。复用 `SyncHttp`、`SyncRound`、`NativeCore` 和 `zapime-sync::client`。终止证明留在原生执行范围，从已认证的原始响应得到后立即用于预检与排队。
- 日常路径先用本机新建、能验证属于当前授权范围的待发操作验收真实双端闭环。存量路径另用来源在排队之前即可验证、初始无待发操作的一条记录跑真实终止拉取、排队和回执。当前 records-only 备份只有记录和来源字段，缺少可信账号出处，事后进行本机账号绑定也无法证明其历史来源。来源无法核实的导入资料保留本机并提示处理。如果需要新格式或新的可信来源机制才能验证正例，单独明确范围，保留存量分项待解决。同步下载只更新本机，避免写回成新上传。
- 授权把页面展示的资料范围绑定到当前的本机工作区。仅纳入有可核实本机来源、当前允许类型、版本一致且通过已知远端修订、唯一性和墓碑检查的记录。
- 新增原生授权入口前验证其能在同一受控边界复核本批范围和选择版本，并生成有限不可变操作。不得把现有 `confirmed=true` 当成长期授权的实现。`stage_next` 会合并未冻结操作并从全局队列取最早项，必须在合并或暂存前做范围和关联检查，历史队列保持原有顺序和冻结字节。认证页冲突整页回滚，游标保持原值。
- 自动执行仅在登录开启且密钥就绪、主 App 启动或回前台、前台网络恢复等已确认时点触发。相同目标每次只运行一轮，合并重复触发。沿用现有有界分页、每轮 16 条上限、合作取消和有限重试边界。每次发送前冻结请求，重试使用原字节。只有核验并持久保存的 ACK 才更新该版本的确认数。工作队列、认证页游标和本地版本单独维护。

### 4. 验证顺序与接手

1. **Go 与共享层。** 用隔离的真实 OIDC 测试账号和 PostgreSQL 验证登录、绑定、设备限额、拒绝与竞态，并执行 `ZAPIME_REQUIRE_DATABASE=1` 的 Go `-race` 门禁。共享层执行工作区测试、格式及严格 Clippy，覆盖账套、来源、撤销、范围和冻结请求。服务端备份验收需包含新身份授权数据，恢复后先验证绑定再发凭据。
2. **Android。** 先跑 JVM 身份/调度策略和本机 JNI/Keystore/SAF 探针，再在真实服务上核实际浏览器回跳及 Android 发起的 HTTPS 双端闭环。API28 系统信任库例外沿用 ADR-023，API35/36 使用本平台实际可用的生产信任路径，证据分别记录。验证仅登录零资料传输、前台自动、离线恢复、快速关闭/换号、丢回执、>16 条、冲突、旧墓碑与输入法回归。
3. **当前接手点。** 主机 OIDC 已通过。下一步用其签发的访问令牌验证 Go 对签发者、目标资源和身份的边界，以及真实 PostgreSQL 中的绑定、owner 授权和一次设备领取。Android 回跳另需隔离环境，其证据和主机结果分别记。准备真实外部账号或域名时按各自范围授权。

后台长期调度、自动传钥、跨账号资料迁移、冲突解决页和公开注册作为后续独立候选事项。当前设计分支记录方案，实施按仓库规则拆独立分支与 PR。
