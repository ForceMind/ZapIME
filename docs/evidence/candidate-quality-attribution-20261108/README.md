- **可见候选缺失**：`h20/c01/c03/c05/c06` 在两个模式、两个运行库均缺失。它表示目标不在这一可见页，不证明整个词库没有该词。统计继续按 64 分母记零；重排只排列已有 ID，无法修复这些目标的覆盖，不能偷偷添加 ID 或修改预期。
- **九键重排伤害**：唯一上下文退步为 `n04`（冻结目标“存档”），`engine:1` 第 2→第 5，跌出前三；空上下文第 2→第 4。上下文无首选损害不等于没有排序伤害。九键另外三例首选改善仍保留，不能通过关闭全部九键增强后只报告这一例恢复来宣称整体改进。
- **空上下文原错误**：v3 退步 `h08` 第 5→7、`h18` 第 2→3、`n04` 第 2→4、`n07` 第 2→4，全部原样保存。它们来自 native 无条件诊断，不是 Android 实际发送了空可信上下文的证明；Android `canRank()` 仍要求 `rankingContext.hasContext()`。
- **补全/部分项**：补全两项可见但不进入评分，四项缺失；六个部分拼音目标可见但不评分。完整阅读、原始输入消费和最终可见槽位条件维持原样，不能把这些保守保护当作模型已经判对或漏跑失败。
- **个人规则**：六项目标均为受保护槽，模型可评分同页其他候选，但不能移动这些目标。5/6 首选是冻结个人偏好的结果：`r02` 显式固定第 2 位，因此不能把它“优化”为第 1 位。个人规则的统计不是模型语言能力，也不是用户分布。
- **上下文边界**：两个空上下文 fixture 在 native 诊断中分别评分或因候选不足而跳过；四个 64 码点 fixture 含重复合成字和补充平面字符。6/6 保留不能证明自然长上下文质量、Android 的 EditorInfo/选择/隐私生命周期，或四端宿主行为。

全部上下文归因分区为缺失 5、目标保护/不可评分 14、候选池不足 2、改善 14、退步 1、不变 28，总计 64；空模式为 `5/14/2/2/4/37`。`attribution.json` 保留每个缺失/退步的原 ID、原名次和评分池大小。

## 产品接缝核对与下一步约束

所核 Rust `ranking.rs` 与报告记录的源 SHA 相同。现有 `exact_ranking_reading()` 对全键比较完整 canonical pinyin，对九键按完整数字/已锁定字母逐位匹配，拒绝 fuzzy/corrected reading；引擎消费完整输入仍为另一必要条件。`n04` 冻结输入只有数字、没有显式拼写选择，不能把不同但合法数字读音的候选称为读音约束绕过。现有真实读音锁定回归也继续保留。

另作过本地辅助诊断：旧 release core SHA `2569edfe66ebcdcb58ff677ab939f54b50de6b0f4d5955ed39876c4380954b60` 的同输入候选页，结合固定 8M/官方 ORT1.28.2，复现“存档”后退；领先项包括同数字歧义解码，参与字符均在固定词表中。因此没有据此认定 OOV 或 JNI 排列错误。该旧 core 的构建身份不同于本次 CI `c3c8a20e…`，只作为查因线索，不纳入以上重算指标，也不宣称执行了新源码 Android。

目前可证明的是 LM-only 九键歧义语义排序不足，尚未证明能通过一个确定的源码错误修复解决。限制 Generated 候选、只在相同音节组内重排、融合基础频率或设定名次阈值都属于新的排序策略，会影响已有改善；不能针对 `n04` 在本集上试出一个参数后直接称真实质量提升。产品代码尚未改动。下一步应先单独固定策略与不退化门槛，再在不改本集预期/不添加候选 ID 的条件下做完整配对结果；发现可独立复现的读音/来源/上下文接缝错误时，另建产品回归和修复。
