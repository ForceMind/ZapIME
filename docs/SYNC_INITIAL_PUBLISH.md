# 备份恢复后的首次发布：显式候选队列安全边界（开发中）

Issue [#77](https://github.com/ForceMind/ZapIME/issues/77) 的一个独立、尚未接入 Android 用户界面的切片。它不是开箱即用的云备份，也不表示恢复后的资料已经上传。原有只读 [同步证据分页](SYNC_INVENTORY.md) 不会创建操作；新增代码只有调用方**明确选择、获证并确认**时才插入本地待发快照。

## 不自动上传的原因

records-only 归档恢复会保留记录 ID、修订、设备来源、完整 JSON 内容和删除标记，但不会生成 `operations`。恢复后 `pending_count=0` **不是**云备份完成证明。同一账号可能已经有远端同 ID 的新版本、旧墓碑或者另一设备的唯一性冲突；将 `untracked` 直接视为远端缺失会复活已删除内容或造成数据覆盖。

## 三个单独的步骤

1. **真实服务器认证拉取至 head：** 主机通过现有 HTTPS/设备令牌、账号密钥描述符核验，逐页调用 `client::apply_page_for_first_publish`。只有完整应用终止页（`next_cursor=head`）才返回不可序列化的临时 `TerminalPullProof`；错误、局部页、缺失密钥或本机冲突不会生成该证明。空页本身不含 AEAD 密文，**必须**依赖外层经过验证的真实 HTTPS 身份，不能拿本地伪造 JSON 当远端缺失证据。
2. **逐条本机预检：** `client::inspect_first_publish` 对用户显式选择的记录返回本机修订与当前完整 JSON 字节 SHA-256，生成一次性操作 UUID。禁止任何已知远端修订、既有操作历史、旧墓碑或超出单条加密预算的记录。这里的 SHA-256 是同机快照校验，不发送网络、不展示日志、不充当认证凭据。
3. **独立用户确认后排队：** `client::confirm_first_publish(..., confirmed=true)` 最多选 16 条，并重核账号/密钥材料完整绑定、最新拉取游标、全部记录修订及字节指纹；单事务插入不可变本机操作快照，经现有触发器进入队列。错误时整批回滚。原记录 ID、修订、正文、来源设备、墓碑、已冻结密文和接收游标不变。同一 operation ID/内容重试不再次排队；其他操作历史仍拒绝。

此阶段 **仅排队**；网络仍须沿用已有 `stage_next` 逐条 AEAD 加密、提交持久冻结请求，再由主机显式传输并核对服务器 ACK。没有将加密、网络或 SQLite 移到普通输入线程。服务器在确认 head 之后可能由另一设备写入；此时仍必须由服务端执行 `base_revision=0`、唯一性、账号、权限与幂等约束，绝不能因为本地临时证明而忽略远端冲突。

## 目前仍未完成

- Android 安全交互：显式选择记录、显示警告和总量、用户确认、分批/恢复进度、账号与密钥选择、失败分类。
- 真正 HTTP 适配器把完整终止拉取结果接给此 API，以及相同服务身份、禁重入和取消期间的保存策略。
- 同一账号双端实际冲突、丢 ACK、被撤销设备、唯一性、墓碑保留、历史密钥及恢复归档回放的全栈验收。
- 模拟器 API28/35/36 与三星 S25 实机验收；正式发布与稳定升级签名。

本切片的单元测试使用真实 SQLite 和本机 AEAD，但远端 `Page` 是**合成协议数据**，不代替经过 TLS 验证的真实服务测试。CI、PR 审查未完成前保持草稿，不标记 Issue #77 已关闭。
