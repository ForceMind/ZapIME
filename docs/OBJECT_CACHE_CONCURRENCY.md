本地结果不代表用户服务器或真实R2已部署修复。

## 原缺陷和复现

原 `singleflight.DoChan` 仅合并同key，`WithoutCancel` 使每次缓存未命中的
后台读取在原handler返回后仍可继续。不同key的反复取消可以不断释放HTTP槽位，
而后台fills没有固定总量上限。5秒期限、每次Pull的8个worker及16MiB LRU都
不能替代在途工作容量。新回归在原生产代码上确切观察到第33个后台读开始，
见[保留的失败与验证记录](evidence/cache-fill-bound-20261107/README.md)。

## 实现契约

| 边界 | 当前行为 |
| --- | --- |
| 在途读取 | 每个缓存实例最多32个不同key的fill；HTTP入口只构造一个实例，全部账号/请求共用 |
| 排队 | 新key没有等待队列；满载返回固定内部错误`object_cache_busy`，不创建额外fill goroutine |
| HTTP结果 | 保持既有`503 storage_unavailable`；整页失败，无部分changes或可推进的成功游标，不做自动重试 |
| 同key | 共享一个只读结果和done信号；满载仍可加入；不为已离开的等待者保留列表 |
| 缓存命中 | 不占fill槽位，返回独立字节副本 |
| 取消所有权 | 每个调用方只结束自己的等待；单个或全部调用方取消都不取消其他设备可能共享的fill |
| 独立预算 | Background上下文加5秒期限，不保留首个HTTP请求的上下文值；全部等待者离开后仍可在此预算内有界预热 |
| 真正结束 | 只有后端实际返回、校验及结果处理完成才释放槽位；超时不能冒充物理I/O已经退出 |
| 非协作后端 | 调用方可在fill期限到达时返回；后端继续占槽直到实际返回，迟到成功不缓存，也不放行新读突破容量 |
| 失败 | 后端错误、坏SHA及超时都不缓存；真正退出后可由后续显式请求重试 |

默认32是当前单实例/单进程的容量，不是所有服务副本的总量；N个独立进程
最多各自持有32个fill。若将来同进程构造多个缓存，也分别拥有容量。
该边界限制并发资源，不保证账单总量、账号公平性、恶意快速顺序请求的速率
或后端一定遵守取消。后端长期不返回时宁可保持槽位并拒绝新读，也不能无限
开启替代工作。外部限流、监控与多副本费用预算仍需独立维护。

## 保持的正确性与隐私边界

数据库账号/设备鉴权和撤销检查仍在缓存访问之前。同key由账号UUID和内容SHA
定位；每次回源继续校验SHA，只接受不可变密文。持久Put成功后才可预热，
缓存不能确认真实后端写入。返回值独立复制，不能被其他调用者修改。

备份、完整对象验证与恢复命令仍直接使用持久后端，绕过在线缓存。没有新增
自动上传、后台同步轮询、对象删除或公开CDN。测试只用合成内容，不连接真实
Cloudflare、用户服务器、设备或生产数据库。
